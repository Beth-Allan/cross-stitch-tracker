    **record-detection.ts (NOT cached — called per-request from server action):**
    - Export: `async function detectBrokenRecords(userId: string, session: { date: Date; stitchCount: number; projectId: string }): Promise<BrokenRecord[]>`
    - Import: `prisma` from `@/lib/db`, `getUserTimezone` from `./timezone`, `TZDate` from `@date-fns/tz`, `startOfDay`, `addDays`, `differenceInDays`, `format`, `parseISO` from `date-fns`
    - NO `unstable_cache` — this is called once per session creation, must read fresh data
    - Implementation:
      1. **Best Day detection:**
         - Get user timezone: `const tz = getUserTimezone(userId);`
         - Calculate today's local day boundaries: `const sessionLocal = TZDate.tz(tz, session.date); const dayStart = startOfDay(sessionLocal); const dayEnd = addDays(dayStart, 1);`
         - Sum all stitches for today: `prisma.stitchSession.aggregate({ where: { project: { userId }, date: { gte: dayStart, lt: dayEnd } }, _sum: { stitchCount: true } })`
         - Get previous best day (before today): Fetch all sessions before today, group by local date in JS (same approach as personal-bests.ts), find the max daily sum
         - If today's total > previous best: push `{ type: "bestDay", label: "Best Day", oldValue: prevBest, newValue: todayTotal, unit: "stitches" }`
      2. **Best Session detection:**
         - Get previous best session: `prisma.stitchSession.findFirst({ where: { project: { userId } }, orderBy: { stitchCount: "desc" }, select: { stitchCount: true } })`
         - Important: This query returns the just-inserted session too. To compare correctly, find the best session that is NOT the current one. Use: `where: { project: { userId }, NOT: { projectId: session.projectId, date: session.date, stitchCount: session.stitchCount } }` — or simpler: just find the top session and if it equals the new one's stitchCount AND there's no other session with that count, it's a new record.
         - Alternatively (simpler): get top 2 sessions by stitchCount desc. If the new session is #1 (session.stitchCount >= top[0].stitchCount) AND there was a previous record to beat (top.length > 0 with lower count), it's broken.
         - Cleaner approach: `const prevBest = await prisma.stitchSession.aggregate({ where: { project: { userId }, date: { lt: dayStart } }, _max: { stitchCount: true } })` — this excludes today entirely, so we compare against historical max. Then: `if (session.stitchCount > (prevBest._max.stitchCount ?? 0))` — push record.
         - Wait — sessions from earlier today should also count as "existing". Better: exclude just sessions created in this exact request. Since we don't have the new session ID here, use the aggregate approach: find the max stitchCount from ALL sessions except those matching exact (projectId + date + stitchCount). Simplest: query max stitchCount where `NOT: { AND: [{ projectId: session.projectId }, { date: session.date }, { stitchCount: session.stitchCount }] }`.
         - SIMPLEST correct approach: just get the historical max from all sessions. The just-inserted session IS in the DB already. So find `_max stitchCount` for all sessions, then count how many sessions have that max. If the new session's stitchCount equals the max AND it's the first time reaching that count (check if any OTHER session has that count — if not, it's new), it's a record. BUT this is complex. Use this approach instead:
         - `const allTimeBest = await prisma.stitchSession.aggregate({ where: { project: { userId } }, _max: { stitchCount: true } })` — if `session.stitchCount === allTimeBest._max.stitchCount`, then check if this is the ONLY session with that count: `const countAtMax = await prisma.stitchSession.count({ where: { project: { userId }, stitchCount: allTimeBest._max.stitchCount } })`. If countAtMax === 1, it's a new record (only one session has this value = the one just inserted). Old value = second-highest session.
         - OR even simpler: just get the max stitchCount from sessions BEFORE the insert. Since `detectBrokenRecords` runs after the insert, we need to find the second-highest. Use: `const sessions = await prisma.stitchSession.findMany({ where: { project: { userId } }, orderBy: { stitchCount: "desc" }, take: 2, select: { id: true, stitchCount: true } })`. If sessions[0].stitchCount === session.stitchCount (our new one is the best), old value = sessions[1]?.stitchCount ?? 0. But we need to verify the top is actually our new session (could be an older session with same count).
         - FINAL approach (cleanest): Pre-query the current max BEFORE insertion would be ideal, but we're called post-insert. So: get top 2 distinct stitchCount values. If new session's count > the 2nd value, it's a record. Implementation: get max excluding sessions from today (to avoid double-counting with bestDay logic), compare session.stitchCount against it.
         - Use: `const prevBestSession = await prisma.stitchSession.findFirst({ where: { project: { userId }, id: { not: undefined } }, orderBy: { stitchCount: "desc" }, take: 1, select: { stitchCount: true } })` — wait, we can't exclude "the new session" without its ID.
         - **FINAL DECISION:** Accept that the just-inserted session is in the DB. Query all sessions ordered by stitchCount desc, take 2. If the top session's stitchCount === session.stitchCount and the second session's stitchCount < session.stitchCount, it's a new record. Old value = second session's stitchCount. If there's only 1 session total, it's the first ever = new record with oldValue 0.
      3. **Longest Streak detection:**
         - Reuse the streak calculation pattern from personal-bests.ts
         - Fetch all distinct session dates for user (timezone-aware), calculate longest streak
         - Compare against the longest streak BEFORE today's session. To get "previous longest": compute longest streak from all dates EXCEPT today. If current longest > previous longest, it's a new record.
         - Simple approach: compute streaks with all dates (including today). Then compute without today. If longest_with > longest_without, broken.
    - Wrap the whole function in try/catch. On error, log warning and return `[]` (don't crash session creation over a celebration failure).

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server action -> record detection | detectBrokenRecords runs server-side with authenticated userId |
| server -> client response | brokenRecords array serialized in action response, consumed by client |
| client -> canvas-confetti | Confetti runs on client Canvas, no server interaction |
| client -> sonner toast | Toast rendered client-side, no server interaction |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-21-10 | Tampering | createSession brokenRecords response | accept | Response generated server-side from authenticated queries. Client can only read it, not modify records. Worst case: client ignores it. |
| T-21-11 | Denial of Service | detectBrokenRecords in createSession | mitigate | Wrapped in try/catch — detection failure does not block session creation. console.warn logged for debugging. Session save succeeds regardless. |
| T-21-12 | Elevation of Privilege | detectBrokenRecords userId scope | mitigate | userId comes from requireAuth() in createSession, not from client input. All detection queries scope to `{ project: { userId } }`. |
| T-21-13 | Information Disclosure | BrokenRecord oldValue/newValue | accept | Values are the user's own records. Single-user app — no cross-user data exposure. |
</threat_model>
