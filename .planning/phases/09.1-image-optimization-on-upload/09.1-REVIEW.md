# Phase 9.1: Code Review Report

**Reviewed:** 2026-04-26T15:45:00Z
**Depth:** standard
**Files Reviewed:** 5
**Status:** issues_found

## Summary

Phase 9.1 adds image optimization on upload: cover images are resized to 1200px WebP + 400x400 thumbnail via a new `processAndStoreImage` function, and session photos are similarly optimized in `createSession`/`updateSession`. The implementation is well-structured with good graceful degradation (raw images preserved on processing failure) and solid test coverage for new paths.

Two critical issues found: (1) `updateSession` re-optimizes already-optimized photos on every edit, causing quality loss and a brief broken-image window, and (2) both `createSession` and `updateSession` return a stale session object with a deleted R2 key after successful optimization. Three warnings for missing ownership validation, hardcoded constants, and a convention violation.

## Critical Issues

### CR-01: updateSession re-processes already-optimized photos on every edit

**File:** `src/lib/actions/session-actions.ts:156-169`
**Issue:** When a user edits a session (changing stitch count, time, etc.) without uploading a new photo, the form submits the existing `photoKey` (which is already an optimized WebP from a prior create/update). The code unconditionally checks `if (session.photoKey)` and calls `processAndStoreImage`, which: (a) fetches the already-compressed WebP from R2, (b) re-compresses it through sharp (generation loss), (c) uploads new re-compressed versions, and (d) **deletes the previously-serving optimized image from R2** before the DB is updated with the new key. This causes cumulative quality degradation on each edit and a brief window where the image URL in the DB points to a deleted R2 object.

**Fix:** Compare the incoming photoKey against the existing session's photoKey to detect whether the photo actually changed. Only optimize when the key is new:

```typescript
// Optimize session photo only when it's a NEW photo (not already optimized)
if (session.photoKey && session.photoKey !== existing.photoKey) {
  try {
    const result = await processAndStoreImage(session.id, session.photoKey, "sessions");
    if (result.success) {
      await prisma.stitchSession.update({
        where: { id: session.id },
        data: { photoKey: result.optimizedKey },
      });
    }
  } catch (err) {
    console.warn("Session photo optimization failed:", err);
  }
}
```

The same pattern should be applied in `createSession` (lines 82-95), though it's less likely to trigger there since creation always uses a fresh key.

### CR-02: Returned session object contains deleted R2 key after optimization

**File:** `src/lib/actions/session-actions.ts:99` and `src/lib/actions/session-actions.ts:173`
**Issue:** Both `createSession` and `updateSession` return `{ success: true, session }` where `session` is the object from the transaction -- containing the **raw** `photoKey`. After successful optimization, `processAndStoreImage` deletes the raw image from R2 and the DB is updated with the optimized key, but the returned object still references the now-deleted raw key. Any client code that uses `result.session.photoKey` to display the photo immediately (e.g., optimistic UI update, toast with preview) will get a broken image.

**Fix:** After successful optimization, update the returned session object or re-read it:

```typescript
// In createSession, after the optimization block:
if (session.photoKey) {
  try {
    const result = await processAndStoreImage(session.id, session.photoKey, "sessions");
    if (result.success) {
      await prisma.stitchSession.update({
        where: { id: session.id },
        data: { photoKey: result.optimizedKey },
      });
      // Update the object we return to the client
      session = { ...session, photoKey: result.optimizedKey };
    }
  } catch (err) {
    console.warn("Session photo optimization failed:", err);
  }
}
```

Note: `session` from the transaction is `const` -- either reassign with `let` or spread into a mutable variable.

## Warnings

### WR-01: confirmUpload does not verify chart ownership

**File:** `src/lib/actions/upload-actions.ts:133-176`
**Issue:** `confirmUpload` calls `requireAuth()` to confirm the user is logged in, but never verifies that `input.chartId` belongs to the authenticated user. An authenticated user could write arbitrary R2 keys to any chart's `coverImageUrl`, `coverThumbnailUrl`, or `digitalWorkingCopyUrl` fields by supplying another user's chart ID. This is a pre-existing issue not introduced by this phase, but the function was modified and is in review scope.

**Fix:** Add ownership validation before the update:

```typescript
const chart = await prisma.chart.findUnique({
  where: { id: input.chartId },
  select: { id: true, projects: { select: { userId: true }, take: 1 } },
});
if (!chart || chart.projects[0]?.userId !== user.id) {
  return { success: false as const, error: "Chart not found" };
}
```

Note: This requires changing `await requireAuth()` to `const user = await requireAuth()` to capture the user object.

### WR-02: generateThumbnail uses hardcoded values instead of shared constants

**File:** `src/lib/actions/upload-actions.ts:371-373`
**Issue:** `generateThumbnail` hardcodes `resize(400, 400, ...)` and `.webp({ quality: 80 })` while `processAndStoreImage` correctly uses the shared constants `THUMBNAIL_SIZE` and `THUMBNAIL_QUALITY` from `@/lib/validations/upload`. If the constants are ever updated, `generateThumbnail` will produce inconsistent thumbnails.

**Fix:**

```typescript
const thumbnailBuffer = await sharp(buffer)
  .resize(THUMBNAIL_SIZE, THUMBNAIL_SIZE, { fit: "cover", withoutEnlargement: true })
  .webp({ quality: THUMBNAIL_QUALITY })
  .toBuffer();
```

### WR-03: uploadRequestSchema missing .trim() on string fields per project convention

**File:** `src/lib/validations/upload.ts:25-26`
**Issue:** The `fileName`, `contentType`, and `projectId` fields use `z.string().min(1)` without `.trim()`. Per the project convention in `form-patterns.md`: "always `.trim()` before `.min(1)`" -- without it, whitespace-only strings like `"   "` pass validation. For `fileName` this results in a key with trailing whitespace (e.g., `covers/p1/test-nano-id-   `). For `projectId` this could cause a failed DB lookup that produces a confusing error.

**Fix:**

```typescript
export const uploadRequestSchema = z.object({
  fileName: z.string().trim().min(1),
  contentType: z.string().trim().min(1),
  fileSize: z
    .number()
    .int()
    .positive()
    .max(MAX_FILE_SIZE, "File is too large. Maximum size is 10MB."),
  category: z.enum(["covers", "files", "sessions"]),
  projectId: z.string().trim().min(1),
});
```

## Info

### IN-01: OPTIMIZABLE_CATEGORIES exported but never used

**File:** `src/lib/validations/upload.ts:22`
**Issue:** `OPTIMIZABLE_CATEGORIES` is defined and exported but not imported anywhere in the codebase. It appears to have been added as a future convenience but is currently dead code.

**Fix:** Either remove the export or use it in `confirmUpload`/`processAndStoreImage` to gate which categories get optimization, replacing the hardcoded `"covers"` / `"sessions"` checks.

### IN-02: processAndStoreImage test asserts constructor name which is fragile

**File:** `src/lib/actions/upload-actions.test.ts:413-415`
**Issue:** The test `"calls DeleteObjectCommand with the original raw key after success"` asserts `lastCall.constructor.name === "DeleteObjectCommand"`. Constructor name checks are fragile -- they break under minification and can be unreliable with mocked modules. The test is currently passing because the module is not minified in test, but this pattern is brittle.

**Fix:** Assert on the command's input properties instead:

```typescript
// Assert the delete command targets the correct key
expect(mockSend).toHaveBeenCalledTimes(4);
const lastCallInput = mockSend.mock.calls[3][0].input;
expect(lastCallInput.Key).toBe("covers/chart-1/raw.png");
expect(lastCallInput.Bucket).toBe("test-bucket");
```
